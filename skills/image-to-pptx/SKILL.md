# image-to-pptx スキル

スライドを 1 ページずつ**画像で設計してから**、編集できる pptx に起こす。テキストはテキストボックス、帯やカードは図形、アイコンは正規アイコンで置き、レンダリング比較で崩れを直してから納品する。**生成した画像も受け取った画像も、スライドには貼らない。**

画像を経由するのは、**画像生成モデルの表現力を資料の品質に持ち込むため**。コードだけで図を組むと手持ちの型の組み合わせになるが、画像生成モデルは内容に合わせてレイアウト・図の構造・要素の配置をその場で設計できる。完成形に近い案を先に見ることで、配置と情報の並びをまとめて決められる。

## どこから始めるか

| 渡されたもの | 画像生成 | 変換元 |
|---|---|---|
| 内容だけ（テキスト・Markdown・会話での指示） | **する** | 生成した画像 |
| 参考画像（「この書式で」「こんな構成で」） | **する**。その画像を `reference_image_path` に渡す | 生成した画像 |
| 変換対象の画像（「この画像を pptx にして」） | しない | 受け取った画像 |
| 作成済みの資料への修正依頼 | しない | 後述「[修正を受けたとき](#修正を受けたとき)」 |

上 2 つが標準。**内容しか渡されていなくても画像生成から始める。** それがこのスキルを使う理由で、画像を経由しないなら [../content-to-pptx/SKILL.md](../content-to-pptx/SKILL.md) の担当になる。
3 つ目は、他社の資料・過去の PDF・受け取ったスクリーンショットを編集できる形に起こすときだけ。このときは**元画像に忠実に写し、文言を足さず、削らない**。

1 回の生成で作らせるのは**スライド 1 ページ分の案**で、タイトル・見出し・図中のラベルを短い日本語で含める。文字を抜いた図版だけを作らせない。文字の精度が要るのは画像ではなく pptx 側なので、画像の文字は構図を読むためのものと考える。

MCP が導入されていない環境では画像を作れない。図の構成を会話で決め、[../content-to-pptx/SKILL.md](../content-to-pptx/SKILL.md) で図形とアイコンから直接作る。
登録済みなのに接続できない場合は、**REST を自分で組み立てて呼ばない**。起動コマンドのパスと接続先の設定を確かめて直すか、上の手順に切り替える。

**書式・描画ヘルパー・ビルドは、プラグイン直下の共通の雛形（`template/`）にある。** 変換の成果物もこの雛形の上でビルドする。

## 書式の決め方

1. 会話で明示されたテーマ（ファイルパス）
2. 参考画像から `scripts/extract_style.py` で抽出し、利用者が確認したテーマ（後述）
3. 作業ディレクトリの `deck-src/theme.json`。書式スキルを併用していれば、その書式が適用済みになっている

「元画像の書式をそのまま」「このブランドに合わせる」と指示されたときは**忠実モード**にし、各要素の色・サイズ・位置の実測値をそのまま渡す（ヘルパーはどれも座標と色を引数で受け取るので、テーマを介さずに置ける）。
どちらのモードでも、編集可能性の検証・レンダリング比較・規格の正規化は同じに行う。

## 作業ディレクトリ

利用者が開いているプロジェクト（VS Code のワークスペース、またはエージェントを起動したフォルダー）の中に、資料ごとに新しく 1 つ作る。利用者が場所を指定した場合はそれに従う。プラグイン直下の `template/` をコピーし、入力と切り出しの置き場を足す。
**ホームディレクトリやプラグインの導入先には作らない。** プロジェクトの外に置くと利用者がエクスプローラーからたどれず、プラグインの導入先は更新のたびに一式が差し替わるため成果物が消える。
**env-setup が動作確認に使ったフォルダーや、別の資料のフォルダーを使い回さない。** 1 つのフォルダーに複数の資料が混ざると、`deck.json` を資料ごとに書き換えることになり、どれが最新の成果物か分からなくなる。既存の資料を直すときだけ、その資料のフォルダーで作業する。
書式スキルを併用する場合は、コピー直後にそのスキルの手順で書式を適用してから始める。

```
<work>/
├── source/            変換元の画像（生成したもの、または受け取ってコピーしたもの）と grid-overlay.png
├── assets/icons/      アイコン（書式スキル由来）と追加取得分
├── assets/crop/       元画像から切り出した図版
├── deck-src/<name>.js 生成するスライドの定義
└── preview/           レンダリング結果と compare.png
```

添付された画像はファイルの実体が無いことがある。最初に `source/` へ保存してもらう。以降の座標把握・切り出し・比較には実ファイルが要る。

## ワークフロー

1. **変換元の画像を `source/` に用意する**（上の表で経路を決め、書式は次の順序で決める）。
   - **画像を生成する場合**は `slide-image-gen` を呼ぶ。プロンプトは書式の `imagePrompt` と `colors` から組み立てる（書式スキルを併用していれば、その定義にある）。参考画像を渡されていれば `reference_image_path` に絶対パスで添える

     **`output_dir` には `<work>/source` を絶対パスで渡す。** MCP は別プロセスで、そのカレントディレクトリは起動したクライアントが決めるため、`source/` のような相対パスは作業ディレクトリ基準にならない。生成後に別の場所からコピーする必要が出る。
   - **変換対象として画像を渡された場合**は、それを `source/` にコピーする。画像生成は呼ばない
2. **座標把握**: `uv run <このスキル>/scripts/grid_overlay.py source/<img>.png source/grid-overlay.png` を実行し、出力画像を表示して各要素の px 矩形を読み取る。目測より正確になる。
3. **要素分解**: テキスト / 図形 / 矢印 / 記号 / アイコン / 表に分け、px 矩形と色・文字サイズの当たりを付ける（後述の換算式と対応表）。
4. **テキスト転記**: 画像の文字をネイティブのテキストとして起こす。**変換対象として渡された画像の場合は、誤字・全角半角・記号・数字・単位を元画像に一致させ、言い換えや要約をしない。** 自分で生成した案から作る場合は、文言を整えてよい（後述）。
5. **アイコンと図版**: 作業ディレクトリのアイコン（`assets/icons/`）で足りなければ `assets/icons/icons.json` に足して `uv run tools/fetch_icons.py` で取得する。正規アイコンで代用できない独自の図版・写真だけ切り出す。

   ```bash
   uv run <このスキル>/scripts/crop_assets.py source/<img>.png assets/crop \
     '[{"name": "diagram", "box": [793, 164, 1016, 496], "autotrim": true}]' --map assets/crop/placement.json
   ```

   矩形は広めに取って `autotrim` に詰めさせる。近接するラベル文字を矩形に含めない（含めると編集できない文字になる）。`--map` が出す px 矩形と同座標・同サイズで配置すれば位置が合う。
6. **pptx 生成**: `deck-src/<name>.js` にヘルパーで定義し、`deck.json` の `parts` を差し替えて `node build.js --name <name>` を実行する。しおり名・規格の正規化と検査・PDF・PNG まで済む。
7. **レンダリング比較**: `uv run <このスキル>/scripts/render_and_compare.py <name>.pdf preview --source source/<img>.png` で `preview/compare.png` を作り、元画像と上下に見比べる。**1 巡で読む画像は 1 枚にする。** 比較画像を読んだら、同じページの `preview/<name>-NNN.png` は読まない（比較画像の下段が同じもの）。
8. **補正**: 崩れを直して 6〜7 を繰り返す。**最低 1 回は補正する。** 位置を詰めるときは、`uv run <このスキル>/scripts/grid_overlay.py preview/<name>-001.png preview/grid-001.png` のようにレンダリング結果にグリッドをかけて測る。元画像に忠実に写す場合で、元画像とのずれが残るときは、手順 2 のグリッド画像で px 矩形を読み直す。
9. **検証と納品**: `uv run <このスキル>/scripts/inspect_pptx.py <name>.pptx --json validation.json` で警告 0 を確認する。`inspect_pptx.py` が見るのは編集できるかどうかだけで、崩れと規範は見ていない。崩れは手順 7〜8 の比較で確かめる。**全ページの体裁と文章規範の検査（[../pptx-lint/SKILL.md](../pptx-lint/SKILL.md)）は、利用者が明示的に求めた場合だけ呼ぶ**（全ページの PNG を読んで規範と照合するため、時間とコストがかかる。呼ぶときは作業ディレクトリと、元にした原稿があればそのパスを添え、作成・変更したのが資料の一部であれば `--pages` でその範囲も添える）。pptx と同名の PDF も添える。
10. **完了の報告**: 成果物の pptx と PDF は、**絶対パスで**示す（`PowerPoint: <work の絶対パス>/<name>.pptx`、`PDF: <work の絶対パス>/<name>.pdf`）。ファイル名やリンクの表示名だけにしない。作業ディレクトリは資料ごとに異なり、表示する画面によってはリンク先が見えないため、利用者が成果物を見失う。修正して再ビルドしたときの報告も同じ。PDF を出せなかった場合は、パスの代わりにその理由を書く。全ページの体裁と規範の検査（pptx-lint）を実施していなければ、そのことと、求めれば実施できることを 1 行添える。

## 生成した案から作る場合

自分で生成した案は**設計図であって、写す対象ではない**。構図・ゾーニング・矢印の流れは活かし、中身は次のように整えて作る。

- 画像の下部にまとめ帯や結論の帯があれば落とし、主張はキーメッセージへ畳む
- 図だけで終わらせず、表・箇条書き・本文の説明を足して、初見で分かる密度にする
- 図の各パーツに一言の添えテキストを付ける。図の説明文は図の上に置く（図の直下には置かない）
- ピクトグラムは元画像から切り出さず、`assets/icons/` の Fluent アイコンに置き換える。独自のメタファー画だけ切り出す
- 画像内の文字は生成モデルが書いたもの。そのまま使わず、書式スキルの文章規範に合わせて直す

レンダリング比較（手順 7）で見るのは、元画像との一致ではなく**崩れ**（文字の折り返し、線の消失、要素の重なり、ラベルの隠れ）になる。中身を足した分は元画像と違っていて正しい。

## 複数ページの資料

**ページごとに「案を生成 → 変換」を繰り返す。** 画像生成 MCP は 1 回の呼び出しで 1 枚を返すので、ページ数だけ順に呼ぶ。サーバーが呼び出しごとに別リージョンへ分散するため、続けて呼んでよい。

- 定義はページごと、または章ごとに `deck-src/<name>.js` へ分け、`deck.json` の `parts` に順に並べる
- 生成画像は `source/<name>.png` のようにページと対応する名前で保存する。どの定義がどの案から起きたのかが後で分かる
- **1 ページごとに全体をビルドし直さない。** `node build.js --pages <範囲>` で作ったページだけ PNG にして当たりを見る
- pptx-lint を求められた場合は、数ページたまってから [../pptx-lint/SKILL.md](../pptx-lint/SKILL.md) にかける。ページ単位で毎回呼ばない。そのとき `--pages` で作成したページの範囲を添える

資料全体の構成（章立て、ページの並び、前後の関係）は書式スキルの規範に従う。1 ページずつ作っていても、隣接するページで同じ図を 2 回描いたり、前方参照を作ったりしない。

## 修正を受けたとき

作成済みの資料への修正では、**画像生成からやり直さない。** 成果は `deck-src/` の定義ファイルに残っているので、そこを直して再ビルドする。画像も作業ディレクトリもそのまま使える。

| 修正の内容 | 進め方 |
|---|---|
| 文言、数値、色、強調、要素の位置、表や本文の追記 | 定義ファイルを直して `node build.js --pages <該当ページ>`。その PNG だけ見る |
| スライドの追加・削除・並べ替え、見出し構成の変更 | 定義ファイルを直して再ビルドし、変更したページの PNG を見る |
| 図のメタファーや構図そのものの変更 | 画像生成からやり直し、ワークフローを 1 巡する |

pptx-lint は、修正の大きさにかかわらず、利用者が求めた場合だけ呼ぶ。

**迷ったら先に定義ファイルで試す。** 図の説得力が足りないときだけ画像生成へ戻る。

## 座標と単位の換算

スライドは 13.33 × 7.5 inch（16:9）。元画像が 16:9 なら縦横共通の係数 1 つで変換できる。

```
K = 13.33 / 画像の幅px          inch = px × K
pt ≒ 文字の高さpx × 540 / 画像の高さpx     （スライド高 7.5 inch = 540 pt。漢字は字面がほぼ em）
```

元画像の比率が 16:9 でないときは、比率を保つか 16:9 に収めるかを利用者に確認する。文字サイズは最後にレンダリング比較で詰める。

## 要素の対応

| 元画像の要素 | 変換先 | ヘルパー |
|---|---|---|
| タイトル / キーメッセージ / 見出し / 本文 / 注釈 | テキストボックス | `title` `keymsg` `sec` `BODY` `CAP` `T` |
| 帯・カード・角丸ボックス・番号バッジ | 図形 | `BOX` `OVAL` `PILL` `TAG` |
| 矢印（実線・破線・双方向） | 矢頭付きの線 | `ARROW` |
| 罫線・区切り線 | 線 | `HLINE` `VLINE` |
| ✕ ✓ などの記号 | テキスト（編集できる方を優先） | `T` |
| アイコン・イラスト | 正規アイコンの PNG、無ければ切り出し | `ICON` `IMG` |
| 表（行列が明確） | ネイティブの表 | `TBL` `cell` `hOpt` |
| コード・設定例 | コードボックス | `CODE` |
| 写真・複雑な図版 | 切り出した PNG | `IMG` |

## 守るべき要点

- **スライドを 1 枚画像にしない。SVG を埋め込まない。** `inspect_pptx.py` が検出して警告する。
- 矢印や線の `w` / `h` に負の値を渡さない。右から左・下から上へ引くと出る。PowerPoint はそのファイルを開けないが、LibreOffice も PDF も通してしまう。ヘルパーの `ARROW` を使い、`tools/normalize.py --check` を常に 0 件にする。
- テキストは折り返さない幅にする。細い線は 2.5〜3pt 以上にする（レンダリングの縮小で消える）。
- 正規アイコンは正方形なので、元の矩形に短辺基準で中央フィットさせる。切り出しは元の px 矩形と同座標・同サイズで置く。
- 白背景の切り出しは透過にする（既定のしきい値 248）。文字が焼き込まれた図版は、文字を切り出しから外して別のテキストで重ねる。
- 表やグラフで完全な編集化が難しい部分は画像にフォールバックし、`validation.json` か報告に書く。
- **フォントは `theme.json` の値をそのまま使う。手元に無いことを理由に書き換えない。** pptx に入るのは名前だけで、描画するのは開いた人の PowerPoint。手元のフォントは PDF と確認用 PNG の見た目にしか影響しない。代替で描かれた PNG は字形が違うぶん折り返しも変わるため、最終確認は PowerPoint で行う。

## 参考画像から書式を起こす

書式だけを参考画像から取り、別の内容に適用したいときの手順。

```bash
uv run <このスキル>/scripts/extract_style.py source/reference.png build/style \
  '{"title": [60, 40, 1700, 120], "keyMessage": [60, 140, 1700, 230], "body": [60, 260, 1700, 960]}'
```

1. 領域の px 矩形は `grid_overlay.py` で読む。省略すると帯を自動検出する。
2. `build/style/theme-draft.json`（草案）と `swatches.png`（色見本）ができる。色と幾何は画素から推定した値なので、そのまま信じない。
3. フォントは画素から復元できないため既定値が入る。字形から候補を挙げて利用者に確認する。
4. 草案を `deck-src/theme.json` に置いて見本をビルドし、`render_and_compare.py --source source/reference.png` で並べて詰める（3 往復が目安）。

## 同梱スクリプト

`uv run` で実行すると依存（Pillow / PyMuPDF / python-pptx）が自動で入る。pip で入れてあれば `python3` でもよい。

| スクリプト | 役割 |
|---|---|
| `scripts/grid_overlay.py` | 座標把握用のグリッド画像 |
| `scripts/crop_assets.py` | 矩形の切り出し（白背景の透過、`autotrim`、`--map`） |
| `scripts/extract_style.py` | 参考画像から theme.json の草案とスウォッチ |
| `scripts/render_and_compare.py` | pptx / PDF → 全ページ PNG、元画像との比較画像 |
| `scripts/inspect_pptx.py` | 編集可能性の検証（全面画像・SVG・テキスト 0 件を警告） |

書式の値とヘルパーの引数は [../../template/README.md](../../template/README.md)、pptxgenjs の落とし穴は [../../references/pptxgenjs.md](../../references/pptxgenjs.md)、環境の点検は [../env-setup/SKILL.md](../env-setup/SKILL.md)。
