# content-to-pptx スキル

Markdown・テキスト・会話での指示から、PowerPoint スライドをコードで直接組み立てる。
画像を貼るのではなく、テキスト・図形・矢印・表・アイコンとして置くため、出来上がった pptx は PowerPoint でそのまま編集できる。

**このスキルは画像を扱わない。** 入力は文章と会話だけで、画像生成 MCP も呼ばない。
画像を渡された場合、または図の構図を画像で設計してから起こしたい場合は [../image-to-pptx/SKILL.md](../image-to-pptx/SKILL.md) の担当になる。

**描画ヘルパー・ビルド・規格検査は、プラグイン直下の共通の雛形（`template/`）にある。** `../image-to-pptx` も同じ雛形を使う。
色やフォントの値、文章と構成の規範は、併用する書式スキルが与える。

| 使う書式 | 進め方 |
|---|---|
| 書式スキルを併用する | そのスキルの手順に従い、`deck-src/theme.json` とアイコンを差し替える |
| 参考資料の書式に合わせる | 書式だけを参考画像から起こす 1 回限りの準備。`../image-to-pptx/scripts/extract_style.py` で草案を作り、`deck-src/theme.json` に置く |
| 指定しない | 雛形に同梱の既定テーマ（グレー基調）がそのまま使われる |

資料の元になる内容（Markdown・テキスト・会話での指示）は呼び出し側が用意する。
本スキルは、受け取った内容を所定の書式のスライドに落とし、PowerPoint で開ける pptx として出力するまでを担う。

## 作成フロー

### 1. 共通の雛形を作業ディレクトリへコピーする

```bash
cp -r <プラグイン>/template/. <作業ディレクトリ>/
cd <作業ディレクトリ> && npm install
```

Windows（PowerShell）は `Copy-Item -Path "<プラグイン>\template\*" -Destination "<作業ディレクトリ>" -Recurse -Force`。

コピー先のファイルは自由に編集してよい（スキルを更新しても上書きされない）。
そのまま `node build.js` を実行すると同梱の例（1 枚）が出るので、環境が動くことを確認できる。構成とヘルパーの引数は [../../template/README.md](../../template/README.md)。

### 2. 書式を適用する

書式スキルを併用する場合は、コピー直後にそのスキルの手順で `deck-src/theme.json` とアイコンを差し替える。
そうでない場合は `deck-src/theme.json` を直接書き換える。**1 か所で全スライドに反映される。**
フォントは画素から復元できないため、参考画像から起こしたときは候補を挙げて利用者に確認する。

### 3. スライドを定義する

- 定義は `deck-src/<name>.js` に書き、`deck.json` の `parts` にファイル名を追加する（既定の `example` は外す）。
- **pptxgenjs の `addText` / `addShape` / `addTable` を直接呼ばず、`lib.js` のヘルパーだけを使う。** 足りない表現はヘルパーを `lib.js` に追加してから使う。直呼びは書式のずれと、PowerPoint で開けないファイルの主因になる。
- **既存の見本から最も近い型をコピーして書き換える。座標を発明しない。** 書式スキルを併用していれば、そのスキルが型の一覧となる見本を持っている。
- 表・箇条書き・コードはヘルパーで直接作る。図が中心のスライドは後述「図の作り方」に従う。

### 4. ビルドする

```bash
node build.js              # pptx → 規格の正規化と検査 → PDF → PNG
node build.js --no-pdf     # pptx と規格検査だけ（LibreOffice が無い環境）
node build.js --pages 3-5  # PNG にするページを絞る
node build.js --parts ch01 # 読み込むパーツを絞る（deck.json より優先）
```

規格違反が残れば PDF を出さずに止まる。無い道具があればその段階で止まらず、できたところまでを報告する。`soffice` を直接呼ばない。

### 5. 目視で検証する

- **ここで読むのは代表 1〜2 枚まで。** 作った直後の当たり確認に留める。PDF は直接読まない（読み込みが環境に依存するため、PNG の方が確実）。
- **全ページの検証は [../pptx-lint/SKILL.md](../pptx-lint/SKILL.md) に任せる。自分で全ページを読まない。** 作業ディレクトリを添えて呼ぶと、ページ番号付きの指摘だけが戻る。**既存の資料に数ページ足した場合のように、作成・変更したのが一部であれば `--pages` でその範囲も添える。** 添えないと資料の全ページを読むため、触れていないページの分だけ費用が増える。**元にした原稿があれば、そのパスも添える。** 文言・数値・コード・リンク先が原稿と一致しているかまで照合される（欠落と誤転記は体裁の検査では見つからない）。PNG は 1 枚で数千トークンを使うため、全ページを本体で読むとコンテキストが埋まる（Claude Code では別コンテキストで動くので、画像は本体に入らない）。
- 指摘を反映して手順 3 に戻る。

### 6. 修正を受けたとき

定義ファイルを直して再ビルドする。作業ディレクトリと書式はそのまま使える。
**全ページの検査を毎回かけない。** 呼ぶかどうかは修正の大きさで決める。

| 修正の内容 | 進め方 | pptx-lint |
|---|---|---|
| 文言、数値、色、強調、要素の位置、表や本文の追記 | `node build.js --pages <該当ページ>` で、その PNG だけ見る | 呼ばない |
| スライドの追加・削除・並べ替え、見出し構成の変更 | 全体を再ビルドする | 呼ぶ |

## スライドの構造

テーマは次の 4 要素を前提に座標を持つ。書式スキルが値を変えても、構造は変わらない。

| 要素 | 役割 |
|---|---|
| タイトル | その 1 枚で扱う内容 |
| キーメッセージ | 最も伝えたい主張。1 枚に 1 つ |
| 見出し | スライド内のブロックの区切り |
| 本文・図・表・コード | 根拠・条件・具体例 |

**1 スライド 1 論点。** 論点が増えたらスライドを分ける。文体・語彙・禁止表現といった規範は書式スキルが定める。

## ヘルパー

書式は `deck-src/lib.js` が `deck-src/theme.json` を読んで決める。ヘルパーを呼べば所定の書式が付くので、定義側で数値を指定しない。

| ヘルパー | 役割 |
|---|---|
| `slide` / `title` / `keymsg` / `sec` | 白背景のスライド、タイトル（幅に収まらなければ自動縮小）、キーメッセージ、見出し |
| `BODY` / `BULLETS` / `CAP` / `SRC` | 本文、箇条書き（【】で囲んだ語を強調）、図の上に置く説明、最下部の出典行 |
| `T` / `RUNS` / `LINK` | ラベル、部分的に色や太字を変えるテキスト、ハイパーリンク run |
| `BOX` / `OVAL` / `PILL` / `TAG` | 角丸の枠、楕円、見出しピル、危険を示すタグ |
| `ARROW` / `HLINE` / `VLINE` | 矢頭付き矢印（向きは反転指定で表し負のサイズを出さない）、区切り線 |
| `ICON` / `IMG` | アイコン、画像（パスは作業ディレクトリからの相対） |
| `TBL` / `cell` / `hOpt` / `rowH` | 表（主色のヘッダー・白のデータ行）、セル、ヘッダーセルの設定、行高の見積もり |
| `CODE` | コードボックス（コメント・文字列・強調行を配色） |
| `divider` / `subDivider` / `toc` | 章扉、節扉、目次 |

色は `L.C` から役割名で取り出す（`PRIMARY` `DARK` `LIGHT` `TEXT` `MUTED` `DANGER` `SAFE` など）。**役割名で書けば、テーマを差し替えても定義を直さずに済む。**
引数の詳細は [../../template/README.md](../../template/README.md)、pptxgenjs 側の技法と落とし穴は [../../references/pptxgenjs.md](../../references/pptxgenjs.md)。

## 図の作り方

- 表・箇条書き・コードはヘルパーでネイティブに直接作る。
- 図が中心のスライドは、**絵にする 1 論点**を決めてから描く。それ以外の情報（手順の一覧、設定値の列挙、判定のルール）は表・本文へ降ろす。
- 一直線のフローにしない。境界・分岐・入れ子・対比のいずれかの構造を持たせ、各要素に一言の添えテキストを付ける。同格の要素は同色にする。
- 図は `BOX`（ゾーンは `LIGHT` の塗り、要素は白箱に `PILL` の見出し）、`ARROW`、`ICON` で組む。
- アイコンは `assets/icons/` の PNG を `L.ICON(s, "<名前>", x, y, 0.5)` で置く。**書式スキルが一式を配置する。** 足りないものは `assets/icons/icons.json` に `{ "name": "<意味>_<色役割>", "icon": "<prefix>:<名前>", "color": "<16 進 6 桁>" }` を足し、作業ディレクトリで `uv run tools/fetch_icons.py` を実行すると取得できる。名前は [Iconify のアイコン一覧](https://icon-sets.iconify.design/)で確認する（存在しない名前は取得に失敗する）。

**図の構図を画像で設計したいときは [../image-to-pptx/SKILL.md](../image-to-pptx/SKILL.md) を使う。** そちらは画像生成 MCP で 1 枚の案を作り、それを設計図としてネイティブ要素に起こす。本スキルは画像を扱わないので、図はヘルパーの図形とアイコンで直接組む。

## PowerPoint で開ける pptx にする

**PDF が出せたことは、PowerPoint で開ける根拠にならない。** pptxgenjs の出力には PowerPoint が破損と判定する規格違反（代表は右から左へ引いた矢印の負のサイズ）が混じることがあり、LibreOffice も python-pptx も通してしまう。

- `build.js` は生成のたびに `tools/normalize.py` で修正と検査を行い、違反が残れば PDF を出さない。
- ヘルパーを使っていれば負のサイズは出ない。直書きした `addShape` からは漏れるため、常に検査 0 件にしておく。

違反の種類と切り分けの落とし穴は [../../references/pptxgenjs.md](../../references/pptxgenjs.md)。

## 長い資料の運用

- 章ごとに `deck-src/ch01.js` のように定義ファイルを分け、`deck.json` の `parts` に順に並べる。`--parts` で章単位のビルド、`--pages` で差分ページだけの PNG 化ができる。
- 正は `deck-src/` の定義ファイルにあるため、会話を compact しても続きを作れる。区切りは章の切れ目で取る。

## スキルを重ねる

このスキルは技術の土台であり、直接編集すると更新で失われる。書式・規範・案件固有のルールは別スキルとして重ねる。

| 変えたいもの | 置き場所 |
|---|---|
| 色・フォント・サイズ・座標 | 書式スキル、または作業ディレクトリの `deck-src/theme.json` |
| 文体・語彙・禁止表現・構成の規範 | 書式スキル |
| 案件・部門固有の用語、章構成、原典 | 別スキル（例: `my-<案件>-docs`）。このスキルと併用する |

```markdown
---
name: my-example-docs
description: <案件名>の資料に固有の記載ルール。<案件名>の資料の作成・修正でトリガー。
---
書式と文章の規範は書式スキルに従う。本ファイルは差分のみを定める。

## 用語
- 「◯◯」ではなく「△△」と書く
```

案件スキルの description には「スライド作成」のような汎用語を入れず、案件名だけで発火させる（このスキルとの同時発火を避ける）。

## 依存

| 区分 | 必要なもの | 用途 |
|---|---|---|
| PowerPoint の生成 | Node.js、pptxgenjs（作業ディレクトリでの `npm install`） | pptx の生成、PDF のしおり名 |
| 規格の検査 | Python 3（標準ライブラリのみ） | 規格の正規化と検査 |
| PDF と画像への変換 | LibreOffice、日本語フォント、PyMuPDF または poppler の `pdftoppm` | PDF 変換、PNG 化、目視検証 |
| アイコンの追加取得 | uv | `uv run tools/fetch_icons.py` が依存を解決する |

無い道具があればその段階で止まらず、できたところまでを報告する。環境の点検と導入は [../env-setup/SKILL.md](../env-setup/SKILL.md) が OS 別に案内する。
