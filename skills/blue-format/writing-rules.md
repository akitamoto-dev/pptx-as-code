# 文章と構成の規範

書式の数値はヘルパー（`deck-src/theme.json`）が持つ。本ファイルは「何を、どう書くか」の正本で、他の文書には同じ規範を書かない。

## 1. スライドの階層

- **タイトル**: 名詞の体言止め。そのスライドの主概念だけを置き、副次的な訴求（配置・手順・上限など）はキーメッセージに担わせる。「―」による補足や疑問文にしない。「の」の連続や、章名との語の重複を避ける。何についてのスライドかタイトルだけで判別できるようにする（認可の話なら「動作モードと認可の設計」）
- **キーメッセージ**: 主語と述語のある完全な文。ですます調。1 文なら句点なし、2 文なら 1 文目だけ句点。最大 2 行に収める。スライド全体を総括し、最も訴求したいことを書く場所で、背景や前提の説明から入らない。本体に書いていない用語を出さない（出すなら本体に説明を置く）。本体の項目名を列挙せず、共通する性質を述べる。「〜が必要です」「〜が重要です」の規範表現で言い切り、「〜して初めて機能する」のような誇張的な完成条件を使わない。書いたら音読し、人が口頭で説明する文として自然かを確かめる
- **＜見出し＞**: 全角の山括弧。短い名詞句（漢語）で、主張・説明句・個数を入れない（個数は世の中で定まっているものだけ可）。比較の見出しは何と何を比べるかを明示する。疑問形・動詞句にしない。直下に、そのブロックが何を示すかを述べる一文を置いてから図・表・箇条書きに入る。＜○○とは＞は新しい概念の初出時だけ。形態や定義を導入する冒頭の＜概要＞は可。複数の＜見出し＞は縦に積む（見出し → 内容 → 次の見出し → 内容）。横に並べるのは、各内容が 1〜2 行で見出しが 2 つだけのときか、明示的に対比するときに限る
- **本文**: である調か体言止め。1〜3 文の段落に収め、重要な箇所は太字と濃い青で強調する。理由や条件を 3 点以上並べるときは箇条書き（見出し語を太字にし、枠や背景色は使わない）。用語や項目の定義は「ラベル：値」。図に書いた内容を本文で繰り返さない。1〜2 行しか置けない＜見出し＞は独立させず上のブロックへ統合する
- **出典**: 根拠が対応する本文中の語句や文にリンクを埋め込む（本文と同じサイズ、青、下線。リンクを外しても自然に読める文にする）。最下部の行は短い出典名と確認日の補足で、本文中リンクの代替にしない。事例は出典を示せるものだけを書き、伝聞は書かない

## 2. 論点と自己完結

- 1 スライド 1 論点。論点が 2 つ入ったら分割する。説明に混ぜる軸（時間・担当・可否）も増やさない
- 1 枚だけ配布されても分かる。章番号参照、「次のスライドで」、「本資料では」、他スライドで定義した番号・ラベルを書かない。丸数字は同じスライド内で定義し、名称を併記する。後で初出になる用語や枠組みに触れない（前方参照の禁止）
- 読者が知っている基礎動作を再説明しない。方式の紹介は、方式名・提供状態・動作・返却内容の表で俯瞰してから詳細に入る。詳細は概要・実装例・利用前提・制約を同じスライドで結び付け、重要な条件を発表者ノートだけに置かない
- 初出のパラメーターや略語は「何を指定し、何が変わるか」を文で説明する。「最大 100」のように対象や単位を省略しない
- 一般論を主文にし、図に固有の値は「例えば」「（このケースでは）」で例だと示す。対策の文には「誰が・どこで」を入れる
- 概念の導入は「一般的な説明 → 名称」の順。未導入の名称を主語にして始めない

## 3. 表現の選択

| 論点の性質 | 表現 |
|---|---|
| 複数案の違い | 表。青ヘッダー、データ行は白。全行で同じラベルを同じ順序に並べ、縦に読んだときの差分が見えるようにする |
| 関係・境界・分岐・時間差 | 図（構造図） |
| 手順・要件・観点の列挙 | 箇条書き |
| 主張・結論・理由 | 文章。背景色の枠で囲まない |
| 設定やコマンド | コードボックス。編集できるテキストにし、内容に即した見出しと前提の説明を添える |

- 表と図と文章の複合構成が普通。絵だけ、図 1 つで余白が大きい、語句だけの図で情報量を薄めない
- 説明が長いときは捉えやすい単位に分けて箇条書きにする。並列の注意点は中黒、定義は「ラベル：値」。同じセルで両方を混在させない
- 文字を大きくするために説明を削らない。入らないときは、文字を小さくする前に列・改行・抜粋を見直し、独立した論点だけを分割する
- 手続き・段階・関係を含む概念を文章だけで済ませない。段階に分解して番号付きの図にし、本文は要点にとどめる

## 4. 図

- 一直線のフローにしない。境界・分岐・入れ子・対比・時間差のいずれかの構造を持たせ、論点が図から読み取れるようにする
- 「絵にする 1 論点」を決めてから描く。手順の一覧は表、上限や設定値の列挙はチップ、判定ルールは本文へ降ろす
- 図の各要素（箱・ゾーン・矢印・アイコン）に、それが何をするものかの一言を添える。ラベルはそのスライドの論点における位置づけを表す語にし、並列するラベルは粒度をそろえる
- 番号は順序を示す用途だけ。別の要素との対応付けに使わない。対応先が無い列挙にはアイコンを置く
- 説明文は図の上（＜見出し＞ → 一文 → 図）。図の下にキャプションを置かない。「図は〜を示す」「下の図のとおり」と図を名指ししない
- 時間軸の線と「時間 →」のラベルを足さない。段階に紐づかない共通施策は、段階の図に混ぜず全幅の帯として別に置く
- 対比は左右対称にする。同じスロットに同じ軸の内容、方式名は同じ語形、片方だけに帰結や色を付けない。「A ではなく B」を訴えるときは B の構成図を主役にし、A は図の中の点線と注記で示す。推奨などの評価ラベルは図に貼らず本文で述べる
- 同じ構造を持つ技術は同じ構図で描く。同じ主題の図を 2 つに分けず 1 つに統合する。図は左に寄せて小さくせず、全幅に大きく描いて説明は下段に置く
- 図の目的は手触りのある理解であって格好よさではない。写実的・雰囲気重視のイラストにしない。矢印・重なり・入れ子・アイコンで構造の豊かな図にする
- 矢印は矢頭付きの図形（LINE と endArrowType）。▶ ▼ などの文字を矢印代わりにしない。細い線は縮小で消えるため 2.5〜3pt 以上にする
- 図中のラベルや表のセルなど面積の限られる要素は、判読できる範囲で theme.json の minFontSize より小さくしてよい。統制や仕組みの解説は、実際の構成図の中に番号付きで配置して示す
- アイコンは正方形。カードの中は 0.5〜0.9 インチ、見出しの脇は 0.3〜0.5 インチ、図の主役は 1.2〜2.0 インチが目安。細い線の字形は縮小で消えるため、小さく使うときは塗りのある字形（`-filled`）を選ぶ
- アイコンに文字を重ねない。ラベルはアイコンの右か上に別のテキストとして置く。表のセルに画像を入れない（行の高さが崩れる）。必要ならヘッダー行の脇に小さく添える

## 5. 色

- 青の濃淡・白・グレーで構成し、強調は濃淡で表す。黄・橙・緑を安易に足さない
- 赤は攻撃の起点・最終的な被害・禁止だけ。1 枚の図の中で最小限にし、並列する項目のうち 1 つだけを赤にしない（同格は同色。差は太字で）
- 同格の並列要素に別々の色を割り当てない。色の違いは意味や重要度の違いとして読まれる
- 補足・結論・注記を背景色の枠で囲まない。色付きの面は図の構成要素だけ。本論に対する注意は右下に寄せ、背景を敷かず赤系のアイコンと見出し色で示す
- 表のデータ行は白。色はヘッダーだけ。コードの構文色（コメント緑、文字列橙）は例外だが、危険でない設定行を赤で強調しない
- 薄い青の面の上の文字は本文色にする。青の文字を薄い青の上に載せない
- アイコンの色は下地で決める。白や薄い青の上は主色か濃い青、青地の上は白、危険は赤、安全は緑
- 核心の短い要素は、アイコンと濃い青の太字と薄青の枠で図の要素として示してよい

## 6. 語彙と文体

- 口語・比喩・造語・擬人化・気取った言い回しを使わない。熟語を使う（作らない → 作成しない、行う → 実施する、置く → 配置する、突き合わせる → 照合する、つながる → 結びつく）
- 身近な物への安易な例え（「運ぶ部品」）をしない。正式な技術用語に簡潔な説明を添える。鉤括弧付きの独自ネーミングを作らない
- 置換の例: 関門・壁・隔壁 → 防御層・検証点・境界／弾く → 遮断する／効く → 作用する／穴 → 脆弱性・攻撃面／素通り → 通過／だから → そのため／上流・下流・受け手 → 取り込みの段階・利用先・後段／想起 → 検索・読み出し／物理分離 → 権限の分離／お願いベース → 仕組みとして保証されない
- 「〜になる——これが〜」のような挿入・倒置を使わず、自然な語順の文に分ける
- 「多層化」「全体像」「必要」のような含意の強い語を安易に使わない。推奨パターンは「必要」でなく「有効」。製品名は現行のブランド名で書き、「Web」と表記する
- 図の見た目（「赤い帯」）への言及で説明しない。実体を述べる
- 見出し・ラベル・キャプション・表のセル・目次まで同じ基準を適用する

## 7. 資料の構成

- 一般的な仕組みを先に、製品固有の実装を後に置く。製品固有の内容は 1 枚に集約し、「採用時は最新の製品ドキュメントで確認する」と注記する
- 要素の多い章は「導入 1 枚（全体感の頭出し）＋節扉」で構成し、後続スライドの主要素を導入の名称と呼応させる。概要スライドのタイトルに「全体像」を使わず「〜の概要」にする
- 関連の強いスライドは隣接させる。「何を対象にするか」と「どう成立させるか」は別スライドにする
- 手続き（誰がいつ何をするか）は設計の節ではなく運用の節に置く。俯瞰は節の最後に 1 つの構成図で示す
- 本編の番号体系に載らない補足は「（参考）」を冠する。「系列名：個別名」のタイトルは前段で全体感を出した場合だけ使う
- 外部フレームワークの紹介スライドは原典の事実だけで構成し、独自解釈や独自の括りを混ぜない。正式名称は原典どおり。原典と手元の一次資料で判断し、二次ソースに無いことを理由に削らない
- リスクと対策の表: リスクのタイトルは「何が起きるか」を述語で終わる文にし、対策は動作の名詞句にする。説明文はタイトルの言い換えではなく理由や条件を書く。同じ観点の行はタイトルの語形をそろえる

## 8. レビュー対応

- レビューで出た質問に直接回答するスライドを作らない。回答は会話で行い、資料には一般的な整理だけを載せる。「混同しやすい点」のような、レビュアーの事実に由来する見出しを使わない
- コメントを転写せず、資料の言葉に再構成する。指摘の本質を既存の論理構造に組み込む
- 修正の判断: 文言・色・配置・追記・並べ替えは定義の修正で対応する。図の構図そのものを変えるときだけ構図ドラフトから作り直す

## 9. 納品前チェックリスト

1. 図・表・文章のバランスが取れている（全面が 1 枚の絵になっていない、余白だらけでない）
2. 口語・比喩・造語が残っていない（図中ラベル・表・目次まで）
3. 数の言い切りに出典がある
4. 新しい用語を初出で定義している
5. ＜見出し＞は短い名詞句で、直下に一文がある
6. 下部にまとめ帯やキーメッセージの再掲が無い
7. 出典が本文中のリンクと最下部の行にある
8. 説明文が図の上にあり、本文で図を名指ししていない
9. 図が構造図で、矢印は矢頭付きの図形
10. 章参照・他スライドへの参照・資料自体への言及が無い
11. 青基調で、赤は攻撃・被害・禁止だけ
12. 補足や結論を背景色の枠で囲んでいない
13. タイトルは体言止め、キーメッセージはですます調の完全文、本文はである調
14. `node build.js` が規格違反 0 件で通り、PNG を全ページ目視した
15. 原稿がある場合、文言・数値・コード・リンク先を原稿と照合した
